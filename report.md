## 1. Цель работы
Построить простейшего агента в виде пайплайна: LLM интерпретирует запрос на естественном
языке и возвращает параметры поиска в согласованном формате (структурированный ответ или
вызов инструмента), а обычная программа проверяет эти параметры и выполняет поиск по SQLite.
Дополнительно: повторные попытки при ошибках разбора, журнал выполнения, хранение
состояния диалога вне модели.

## 2. Архитектура
```
запрос ─► ChatPromptTemplate ─► LLM ─► PydanticOutputParser ──┐   (граница with_retry,
          (system: правила +        (qwen3.8-27b,              │    ≤ 3 попыток, только
           format_instructions)      thinking выкл.)           │    OutputParserException)
                                                               ▼
                                   проверка ProductQuery ─► search_products (SQLite, ?-параметры) ─► вывод
                                              └──────────── всё пишется в StepLog ────────────┘
```
Принципы:
* **LLM не пишет SQL.** Она возвращает только `ProductQuery` (категория, макс. цена, сортировка).
  SQL собирает `search.py` из фиксированных фрагментов; значения передаются как `?`-параметры,
  направление сортировки берётся из белого списка. Категория — `Enum`, цена — `int ≥ 0`,
  поэтому строка с SQL не проходит валидацию (проверено в `test_pipeline.py`).
* **Граница retry** проходит *до* поиска: повторяются только генерация и разбор, поэтому
  повтор LLM не приводит к повторному обращению к БД.
* **Состояние** — последний валидный `ProductQuery` — хранится в переменной программы
  (`DialogueSession.current`).
* **Токен** читается из `LLM_API_KEY`; `StepLog` дополнительно маскирует его значение.

Модули: `schema.py`, `init_db.py`, `search.py`, `pipeline.py`, `fakes.py`, `run_lab.py`, `app.py`.

## 3. Часть 1. Базовая цепочка
Промпт: `system` — роль («определи категорию товара, отвечай на языке {language}»),
`human` — `{query}`. Цепочка: `prompt | llm | StrOutputParser()`.

* Типы: `llm.invoke(...)` → `AIMessage` (объект сообщения с `.content`, `usage_metadata` и др.);
  `chain.invoke(...)` → строка: фактически `TextAccessor` — подкласс `str` в новых версиях `langchain-core`,
  который ведёт себя как обычная строка (`'Ноутбуки'`). Парсер извлёк из `AIMessage` только текст `.content`.
* `batch` на трёх запросах вернул `['Ноутбуки', 'Смартфоны', 'Планшеты']` — по одной строке на запрос, порядок сохранён.

## 4. Часть 2. Structured output
### 4.1. Схема (`schema.py`)
| Поле | Тип | Ограничения / умолчание |
|---|---|---|
| `category` | `Enum`: laptop, smartphone, tablet, other | обязательное |
| `max_price` | `Optional[int]` | `ge=0`, по умолчанию `None` |
| `sort_by` | `Enum`: price_asc, price_desc | по умолчанию `price_asc` |

`PydanticOutputParser(pydantic_object=ProductQuery).get_format_instructions()` вставлено в

### 4.2. Тестирование (задание 2.3)
| № | Запрос | JSON | Проверка |
|---|---|---|---|
| 1 | Найди ноутбуки дешевле 70 000 рублей | `{"category":"laptop","max_price":70000,"sort_by":"price_asc"}` | ✅ |
| 2 | Покажи самые дорогие смартфоны | `{"category":"smartphone","max_price":null,"sort_by":"price_desc"}` | ✅ |
| 3 | Хочу посмотреть планшеты | `{"category":"tablet","max_price":null,"sort_by":"price_asc"}` | ✅ |
| 4 | Покажи ноутбуки до 50 тысяч | `{"category":"laptop","max_price":50000,"sort_by":"price_asc"}` | ✅ |
| 5 | Найди холодильники | `{"category":"other","max_price":null,"sort_by":"price_asc"}` | ✅ |
| 6 | Нужно что-нибудь недорогое для учёбы | `{"category":"other","max_price":null,"sort_by":"price_asc"}` | см. ниже |
| 7 | Покажи Apple до 100 тысяч | `{"category":"other","max_price":100000,"sort_by":"price_asc"}` | см. ниже |

Все пять эталонных запросов разобраны верно: категория, ограничение цены (в т. ч. нормализация «50 тысяч» → 50000),
сортировка по убыванию для «самых дорогих», `null` при отсутствии цены, `other` для холодильников.
Каждый ответ прошёл валидацию `ProductQuery`.

Собственные неоднозначные запросы и их интерпретация:
* «Нужно что-нибудь недорогое для учёбы» — модель вернула `other`, цену не ограничила, сортировка по возрастанию.
  Формально ответ валиден, но по смыслу спорный: для учёбы обычно подходят ноутбуки или планшеты, а в запросе нет
  ни категории, ни суммы. Модель не стала угадывать и выбрала безопасное `other` (по правилу «неизвестная категория —
  `other`»), а сортировка по возрастанию цены — разумная трактовка слова «недорогое». Следствие: поиск не выполняется
  и пользователь получает «категория не поддерживается», хотя товары в каталоге есть. Правильнее было бы уточнить запрос.
* «Покажи Apple до 100 тысяч» — модель вернула `other` и `max_price = 100000`. Цена извлечена верно, но бренд —
  не категория (Apple есть и среди смартфонов, и среди планшетов каталога), а схема не имеет поля «бренд», поэтому
  модель не смогла выбрать категорию. Следствие то же: поиск не выполняется, и извлечённая цена теряется. Ограничение
  схемы, а не ошибка разбора; решается расширением схемы (поле `brand`) или уточняющим вопросом.

### 4.3. Режим размышления (задание 2.4)
| Запрос | thinking | Параметры | Время | Токенов на выходе | Начало content | Есть reasoning_content | Парсер справился |
|---|---|---|---|---|---|---|---|
| Нужно что-нибудь недорогое для учёбы | выкл | other, ≤None, price_asc | 1.4 с | 98 | `{"category": "other", "max_price": null, "sort_by": "price_asc"}` | нет | да |
| Нужно что-нибудь недорогое для учёбы | вкл | other, ≤None, price_asc | 1.2 с | 65 | `{"category": "other", "max_price": null, "sort_by": "price_asc"}` | нет | да |
| Покажи Apple до 100 тысяч | выкл | other, ≤100000, price_asc | 2.2 с | 262 | `{"category": "other", "max_price": 100000, "sort_by": "price_asc"}` | нет | да |
| Покажи Apple до 100 тысяч | вкл | other, ≤100000, price_asc | 1.3 с | 75 | `{"category": "other", "max_price": 100000, "sort_by": "price_asc"}` | нет | да |

Выводы по полученным данным:
* **Параметры** при включённом и выключенном размышлении совпали на обоих запросах (`other`, цена и сортировка те же).
* **Время и токены.** Ожидаемого роста при включении режима не наблюдается: время 1.2 с против 1.4 с и 1.3 с против 2.2 с,
  токенов 65 против 98 и 75 против 262. Это единичные замеры, разброс (в т. ч. задержка сети и первого вызова) сопоставим
  с разницей, поэтому делать вывод о «ускорении» от thinking нельзя. Отметим также, что число выходных токенов заметно
  больше длины самого JSON (около 25–30 токенов); почему так — по этим данным установить нельзя.
* **Где рассуждение.** `content` в обоих режимах начинается сразу с JSON (без блока `<think>…</think>`), поля
  `reasoning_content` в ответе нет, парсер справился во всех четырёх прогонах. Т. е. в нашем прогоне рассуждение
  клиенту не пришло ни в `content`, ни в отдельном поле: либо модель на таком простом запросе не стала рассуждать,
  либо сервер не отдаёт его в ответе. Это зависит от настроек сервера.
Рассуждение — это свободный текст, который модель генерирует *до* ответа; парсер ожидает
только JSON-объект, поэтому рассуждение должно оставаться вне текста, который разбирается как JSON
(отдельное поле или удаление блока `<think>`), иначе разбор ломается либо в JSON попадает мусор.
Для задачи извлечения параметров размышление обычно не нужно: схема и правила уже задают ответ.

| | Часть 2 (инструкции формата) | Часть 3.4 (tool calling) |
|---|---|---|

## 6. Часть 4. Retry и журнал (результаты получены офлайн)
### 6.1. Анализ ошибок (задание 4.1, `python test_retry.py`)
| № | Невалидный ответ | Исключение парсера | Исходная причина (`__cause__`) | Этап |
|---|---|---|---|---|
| 1 | `Конечно! Вот параметры поиска: …` (не JSON) | `OutputParserException` | `JSONDecodeError` | разбор текста в JSON |
| 2 | `"category": "fridge"` (вне enum) | `OutputParserException` | `ValidationError` | валидация схемы (enum) |
| 3 | `"max_price": "дёшево"` (неверный тип) | `OutputParserException` | `ValidationError` | валидация схемы (тип) |
| 4 | `"max_price": -5000` (нарушено `ge=0`) | `OutputParserException` | `ValidationError` | валидация схемы (ограничение) |
| 5 | нет обязательного `category` | `OutputParserException` | `ValidationError` | валидация схемы (поле) |

Наблюдения, которые стоит учесть при подборе «плохих» примеров:
* Парсер **прощает** часть синтаксических ошибок: оборванный JSON `{"category":"laptop","max_price":70000`
  восстанавливается (используется разбор частичного JSON) и ошибки не будет — поэтому в примере 1 нужен
  ответ, в котором вообще нет JSON.
* Pydantic по умолчанию **приводит типы**: `"max_price": "70000"` и `70000.0` превращаются в `70000`;
  ошибку дают `70000.5` и `"70 000"`. Поэтому для «неверного типа» взята нечисловая строка.
* Парсер оборачивает `ValidationError` и `JSONDecodeError` в `OutputParserException`; настоящая
  причина доступна через `__cause__`. Именно `OutputParserException` ловит retry.

### 6.2. Retry (задание 4.2)
```python
chain.with_retry(retry_if_exception_type=(OutputParserException,),
                 stop_after_attempt=3, wait_exponential_jitter=False)
```
Максимум 3 попытки включая первую. Retry оборачивает `prompt | llm | parser`; поиск стоит
после границы retry, поэтому не повторяется. При исчерпании попыток `run_query` перехватывает
исключение и возвращает понятное сообщение («Не удалось разобрать ответ модели за 3 поп. …»).
Ограничение по типу исключения важно: сетевые сбои и ошибки программирования не должны
молча перезапускаться как «ошибки разбора».

### 6.3. Журнал (задание 4.3)
События: `request`, `llm_call_start` (номер попытки), `parse_error` / `parse_ok`,
`validation_ok`, `search_start`, `search_done` (число найденных). Фрагмент журнала сценария
«некорректный ответ → корректный» (запрос «Найди ноутбуки дешевле 70 000 рублей»):
```
request            text=Найди ноутбуки дешевле 70 000 рублей
llm_call_start     attempt=1
parse_error        attempt=1  error_type=JSONDecodeError  error=Invalid json output: Конечно! Вот параметры…
llm_call_start     attempt=2
parse_ok           attempt=2  params={category: laptop, max_price: 70000, sort_by: price_asc}
validation_ok      params={category: laptop, max_price: 70000, sort_by: price_asc}
search_start       params={category: laptop, max_price: 70000, sort_by: price_asc}
search_done        status=ok  found=4
```
`search_start` всегда идёт после `validation_ok` (проверяется ассертом в `test_retry.py`).
Токен не попадает в журнал: `StepLog` маскирует значение `LLM_API_KEY` (тест `test_token_not_in_log`).
Дополнительное задание реализовано: `python app.py --confirm` запрашивает подтверждение, если цена не ограничена.

### 6.4. Воспроизводимый тест (задание 4.4)

## 8. Выводы
1. Разделение ролей — LLM интерпретирует текст, программа проверяет и исполняет — даёт
   предсказуемость и безопасность: модель не видит БД и не пишет SQL.
2. Валидация по Pydantic обязательна: ответы модели нужно считать недоверенным вводом
   (ошибки разных типов проявляются на этапах разбора и валидации).
3. Retry повышает устойчивость, но его граница должна проходить до побочных действий;
   число попыток ограничено, а исчерпание обрабатывается явно.
4. Журнал шагов позволяет доказать порядок «проверка → поиск» и разбирать сбои.
5. Tool calling переносит извлечение параметров на сервер, но проверку и исполнение
   по-прежнему должно выполнять приложение.
6. Состояние диалога лучше хранить в программе, а не заставлять модель «помнить» историю.
7. Точность извлечения параметров на реальной модели: 5 из 5 эталонных запросов (2.3) и 11 из 11 в сквозном пайплайне (3.3);
   слабое место — неоднозначные запросы («для учёбы», бренд «Apple»), где модель выбирает `other`, а схема не позволяет
   выразить бренд или уточнение.
8. Режим размышления на этих запросах не изменил параметры; роста времени и числа токенов и рассуждения в ответе
   мы не наблюдали, а для извлечения параметров по схеме он и не нужен.
9. Без базы модель отказывается отвечать о каталоге (ничего не выдумывает, но и не помогает); точный ответ даёт только БД.
10. Расход токенов: при хранении состояния в программе входной контекст постоянен (~740), при передаче истории растёт
    на ~30 токенов за реплику, и модель теряет ограничения (1 ошибка из 7 шагов).

## Приложение. Ответы на контрольные вопросы
1. В пайплайне последовательность шагов фиксирована программой, LLM лишь интерпретирует запрос; в агенте LLM сама выбирает действия и обрабатывает их результаты в цикле.
2. Цепочка — композиция `Runnable` оператором `|`; `StrOutputParser` преобразует `AIMessage` в строку.
3. `system` задаёт роль и правила, `human` — данные пользователя; так проще параметризовать и отделять инструкции от ввода.
4. Structured output — ответ в заданной схеме (JSON/объект), пригодный для машинной обработки, в отличие от произвольного текста.
5. `BaseModel` — описание схемы и валидация; `Field` — описание, ограничения, умолчания; `Literal` (или `Enum`) — допустимый набор значений.
6. У модели нет данных каталога — она может придумать товары и цены; надёжно ответить может только запрос к БД.
7. В части 2 схема в тексте промпта, парсинг/проверка на клиенте; в tool calling схема передаётся API, сервер разбирает вызов в `tool_calls`, а проверка аргументов и действие остаются за приложением.
8. Ответ модели — недоверенный ввод: ошибки и «выдуманные» значения нужно отсечь до обращения к БД; произвольный SQL от LLM опасен (инъекции, `DROP`, утечки данных).
9. Retry нужен для ошибок разбора/валидации (а не для логических ошибок поиска). Повтор с тем же промптом полагается на случайность генерации; исправление с учётом ошибки передаёт модели текст ошибки и обычно сходится быстрее.
10. Состояние хранить в программе (последний валидный `ProductQuery`); на каждом шаге передавать правила, формат, текущие параметры и новую реплику.
